## 二、正确性与健壮性

- **遍历实体时插入实体（UB）**：`processWeaponFire` 在 range-for 里 `spawnProjectile`（会 `push_back` 到从未 reserve 的 `entities_`）。改为两段式：先收集开火意图到成员暂存区，遍历结束后统一发射（同时避免每步堆分配）。
- **越界格被当成"跳过"**：`isPositionWalkable` 里 `if (!inBounds(probe) || isWalkable(probe)) continue;` 与注释"越界视为阻挡"相反，导致"圆心在图内、身体伸出图外"被判可站立。改为让越界格参与圆-矩形判定。
- **胜利判定过早**：击杀最后一个敌人时它可能刚射出一发还在空中的子弹；立刻宣布胜利的话，下一帧子弹打死玩家就会把结算从"胜利"翻成"失败"。现在胜利需要"无存活敌人 **且** 无在飞的敌方子弹"。
- **重开后本局用时不清零**：`elapsedGameTime_` 是外部时钟的拷贝，`reset()` 的归零会被下一步覆盖。新增 `matchElapsedTime()`（本局用时），结算横幅改用它；外部时钟语义保持不变（弹着残影/伤害闪光的年龄计算依赖它）。
- **EQS NaN 防护**：`std::clamp` 对 NaN 原样返回 NaN，会让候选带着 NaN 进入 `stable_sort`（比较器失去严格弱序 = UB）。现在非有限值一律压成 0 分。
- **EQS 候选数量上限**：`gridGenerator` 点数由调用方参数决定，`spacing=1, radius=2000` 会申请约 1600 万个点。现在把半径钳到最多 65×65 ≈ 4.2k 候选，环形生成器同样封顶。
- **EQS 种子注释与实现不符**：种子掺入了 `gameTime`（并非"固定种子"），并对 double→uint32 转换做了取模/clamp，避免负值或超大时间的 UB。
- **`kill()` 与血量不一致**：调试面板会显示 `hp=70/70 [DEAD]`。`kill()` 现在同时清零血量。
- **输入/键位杂项**：`toIndex(Action)` 补上界钳制；键位表打印按键名而不是键码数字。
- **重开语义统一**：面板"重置世界"改为走与回车重开相同的 `restartRun()`（此前不清结算横幅、不拉回相机、不解除冻结）；`World::reset()` 也会把 AI 恢复为启用。
- **HUD 统计恒为 0**：main 为了运行期更换 layer 自己写了一份主循环，绕过了 `GameLoop` 的统计，HUD 上"逻辑步"永远是 0。新增 `GameLoop::recordFrame()`，两处循环共用（截图确认：帧 300 / 逻辑步 149）。
- **`--shot` 语义修正**：原实现只做"只截一次"，且未指定 `--frames` 时默认帧号算成 0（截到几乎空白的第一帧）。现在：未指定帧号时取 `--frames` 的最后一帧，否则取第 300 帧（≈5 秒，敌人已开始交火）；截图后真正退出，与 `--help` 文案一致。
- **无效测试修正**：`EnemyDamagePerSecondStaysWithinSanityBound` 此前恒真（伤害被玩家 100 血封顶，240 DPS 的 bug 也能通过）——现在先把玩家设为不可死再测射速；`ResetRestoresStatistics` 补"先制造非零统计"的前置；`WorldKeepsSimulatingAfterDefeat` 的弱代理断言改为"敌人仍在移动"；`HugeCooldown...` 补下界。
- **新增回归用例**（6 条）：AI 冻结不再开火、删除障碍物恢复可行走、半径伸出地图外判不可行走、撤退方向不反、胜利等敌方弹幕落地、**玩家射击→击杀→胜利的端到端闭环**。
- **清理**：消除全部编译警告（含 `World.cpp`/`Enemy.cpp`/`DebugUI.cpp` 的 nodiscard 与未使用参数）；`--headless` 搭配 `--auto-roll`/`--shot` 时明确提示"该选项在无头模式无效"，不再静默忽略。

## 三、诚实说明：一处结论被修正

报告里曾把"撤退读错黑板键"描述为**敌人会朝玩家冲锋**。实测做了对照实验（把修复临时回退）后发现：由于撤退点每 1.5 秒重选、寻路路径占主导，错误键只暴露在"寻路失败 / 路径耗尽"的降级路径上，**画面上看不到必然的冲锋**。三种断言写法在错误实现下都会通过。

因此：修复保留（语义正确），但回归测试改为断言**行为契约**（脱离威胁、撤退点比自身更远），并在注释里写明了"这条测试能守什么、不能守什么"。

## 三·补：「敌人自己卡住」（用户报告，已定位并修复）

现象：地图边缘（右下）的敌人 15 秒与 30 秒时坐标完全相同，一动不动。

三处缺陷叠加：

1. **导航网格按整除生成**：`gridExtent.y = 1200`、`cellSize = 32` → `1200/32 = 37.5` → 37 行，网格只覆盖到 **y = 1184**，地图最下面 16 个单位没有导航数据。
2. **下边界墙因此完全失效**：边界墙位于 `y ∈ [1200, 1240]`，与网格 `[0, 1184)` 毫无交集，`fillRect` 的相交测试直接 return —— 下边界等于没有墙。（上边界墙只是因为恰好"碰到" `y = 0` 才生效，这就是"上面能挡、下面挡不住"的原因。）
3. **巡逻点校验用了会骗人的判据**：`isWalkable(worldToGrid(candidate))` 只看格心，而 `worldToGrid` 会把地图外的坐标**钳制**到边界格 —— 于是 `y = 1272`（明显在图外）的巡逻点被判成"可通行"并被选中。敌人朝图外硬推，被边界约束顶在 y = 1173；而换点的常规条件是"已到达目标"，够不到就永远不换点 → 永久静止。

修复：

- `World::buildNavGrid` 改用 **向上取整**（`50×38`，覆盖 `[0,1216)`）→ 边界墙与网格有交集，外圈被真正封住。
- 新增 `NavGrid::canStand(world, radius)`：**半径感知 + 越界即阻挡**，作为"这点能不能站"的**唯一实现**；`World::isPositionWalkable` 改为委托它（此前 AI 层各自实现了一份"格心可通行就算能站"的简化版，两把尺子必然打架）。
- 巡逻点选择改用 `canStand`，并且**由远及近试多圈半径**（260/190/130/70）——贴边的敌人至少能在近处巡逻，而不是退化成"原地待命"。
- 新增「迟迟走不到就换点」兜底（2.5 秒无进展 → 强制重选），任何因地形变化而不可达的目标都不会再让敌人永久静止。
- EQS 的掩体/撤退/接近三个查询的候选筛选器同样改用 `canStand`（此前的简化版会把"格心可通行但身体插进墙里"的点选出来，表现为敌人贴着墙推）。

验证：Enemy1 从「15s/30s 坐标完全相同 (986,1173)」变为 `(659,975) → (939,1030) → (959,839)` 持续巡逻；新增 2 条回归用例（`CanStandRejectsOutOfMapAndWallHugging`、`EnemiesNeverFreezeInPlace`）；262 tests 全绿。

## 三·补二：结算用时冻结 + 队伍情报共享（用户反馈）

### 1. 胜利后"用时"还在走

现象：胜负已分，世界还在推进（敌人退巡逻、子弹落地、尸体消失），而结算横幅上的
"用时/坚持"用的是实时值 —— 数字像一块忘了停的秒表。

修法：`World` 新增 `settledElapsedTime()`：**分出胜负那一刻把本局用时冻结**，
之后不再变化；按 N 增兵续战（结果回到 Running）时自动解冻、继续计时。

两个实现细节：
- 判定是**实时**问一次 `outcome()`，而不是读缓存的"上一步结果"——结果可能在
  `update()` 之外改变（调试面板直接造成伤害、按 N 增兵），用缓存会有一帧延迟，
  横幅会显示上一局的数字（这正是第一版实现的问题）。
- 冻结值本身由 `update()` 在判定发生的那一步写入，因此记录的是**准确时刻**，
  而不是"第一次被读到"的时刻。

回归测试：`MatchOutcomeTest.SettledTimeFreezesWhenMatchEnds`。

### 2. 队友之间共享「最后已知位置」

需求：看见目标的敌人要把"目标最后在哪"告诉队友，让没看见的队友有方向可搜。

实现（分层保持不变：敌人之间不互相引用，World 汇总后广播）：
- `World::broadcastSquadIntel()` 每步取全队**最新鲜**的一次目击，写进每个敌人的
  黑板（`world.squadIntelPosition` / `world.squadIntelTime`）；超过有效期
  （`EnemyConfig::squadIntelMemory`，默认 12 秒）就清掉。
- `Enemy::searchLead()` 把"线索从哪来"收敛到一处：**自己的记忆优先，其次是队友
  情报**。搜索分支的条件与目标点都走它，避免"条件成立但拿不到目标"的半挂状态。
- 收到**更新**的报告时会清掉 `searchAbandoned_`——队友刚看到目标，就值得再去
  那边看一眼；同一份旧报告不会反复重置搜索（否则会永远搜索）。

语义边界（刻意守住）：共享的是**情报**，不是视野。收到情报的敌人依然要靠自己的
感知确认才能进入交战分支——能包抄，但不会"共享瞄准"。

细节：`aiDebugString()` 末尾会附 `intel=(x,y)`（仅在情报有效时显示），F3 的
world dump 也能直接看到。

回归测试：`EnemySearchTest.TeammatesShareLastKnownPosition`（传播、被使用、过期失效）。

### 3. 顺带修掉一个被这条测试暴露的既有缺陷

**搜索分支从不请求重新寻路**，而 `updatePathfinding()` 只在 `repathRequested_`
时才重算 → 敌人虽然把移动目标改成了"最后已知位置"，脚下却仍然沿着**上一条路**
（多半是巡逻路线）走：看似在搜索，实际越走越远。

修法两层：
- 搜索动作在"线索换了地方"（偏移 > 48）时显式请求重寻路；
- `updatePathfinding()` 增加系统性兜底：目标点相对"上次寻路时的目标"偏移超过
  ~1.5 格就强制重算。这样任何"改了 moveTarget_ 却忘了请求重寻路"的动作节点
  都不会再沿着旧路径跑偏。

### 4. 顺带把一条脆弱测试改成不依赖采样时机

`EnemySearchTest.ActuallyVisitsLastKnownPosition` 原来断言"跑满 3 秒后的瞬时距离
< 120"。但敌人到达后会立刻"观察 → 放弃 → 走向新巡逻点"，于是恰好在采样那一步
它已经重新走远（实测 122，卡在阈值上判失败）。改成断言**整段轨迹上的最近距离
< 60**——它要证的本来就是"到过那儿"。

## 三·补三：情报范围 / 到点发呆 / 开火节奏（用户反馈第二轮）

三条反馈，全部先实测定位再改。**结论：第三条的主因是"配置被夹回去 + 判据用错数据"，
而不是 AI 逻辑本身。**

### 1. 共享情报的范围

- 有效期 `squadIntelMemory` 12 → **24 秒**（情报留得更久，队友有更多时间赶过去）。
- **阵亡队友的最后目击仍然算情报**：原来 `broadcastSquadIntel` 跳过尸体，
  报告者被击杀的瞬间情报就消失了 —— 而那正是队友最需要知道敌人从哪来的时刻。
- 说明：情报共享**本来就没有距离限制**（全图所有敌人共用一份），
  所以"范围"能扩的是**时效与来源**，不是半径。
- 顺带：赶往线索点时启用冲刺（见下），跨半个地图的支援不再慢吞吞。

### 2. "跑到 last location 点位发呆"

- 观察窗口 2.0 秒 → **0.8 秒**，并且不再是站桩：期间**左右扫视**（朝向摆动 ±52°），
  观感从"到点僵住两秒"变成"到点环顾、没人、走"。
- 新增保护：**报告位置没变就不重新唤醒**（`searchRearmDistance = 120`）。
  队友持续盯着同一点时，情报时间戳每步刷新，原来会把已查看过并放弃的敌人
  反复唤醒回同一个点。
- 回归测试：`SearchHoldLooksAroundInsteadOfFreezing`（对照实验：取消扫视后
  累计转角 0.007 弧度 → 失败 ✓ 有牙齿）。

### 3. "射击间隔很怪、有时射不出来" —— 四个真实原因

实测（玩家绕圈走位、无敌、真实示例关卡、60 秒）改造前：敌人有 **28~34 秒**
处在射程之外，单个敌人只开 22~35 枪，最大间隔 **10.5 秒**。逐个定位：

1. **冲刺配置被夹回去了（最关键）**：`applyMovement` 的速度上限自己写了一套判据
   （只认"撤退时冲刺"），于是 `desiredMoveSpeed()` 里新加的"够不着就全速追"
   完全无效 —— 实测敌人**最高速度永远是 130**，而玩家走速就是 160。
   修复：上限统一走 `desiredMoveSpeed()`。实测最高速度 130 → **240**。
2. **判据用了"只在看见时才更新"的黑板距离**：`kNearestEnemyDist` 在失去视线后
   停止更新（实测真实距离 400+ 时黑板里还写着 13/58/195），用它判断
   "够不够得着"永远不会触发冲刺。改为取**到线索点的实际距离**与黑板值
   的较大者；同时只在"确实在赶路"（正赶往线索点 / 交战中）时冲刺，
   避免巡逻时也狂奔。
3. **追击途中枪口被拽走**：原来"超出射程"直接返回，枪口由 moveDirection 决定；
   等进入射程还要额外花 0.3~0.9 秒重新瞄准（实测占开火间隔约 30%）。
   改为**无论远近都保持枪口指向目标**，进射程即可开火。
4. **到位后干等节流窗口**：选位节流 2.5 秒内不重新评估，而玩家 2.5 秒能跑 450 单位。
   新增"站定 + 目标脱离交战带 ⇒ 立刻重新选位"。
5. 顺带把敌人射程 320 → **400**（玩家是 520，敌人原来很难有机会还手），
   并新增一致性测试 `EnemyWeaponReachCoversItsFiringRange` 把开火距离与
   子弹射程锁在一起（防止以后只调一个 → 子弹半路消失的隐蔽问题）。

**验收**（玩家在开阔地以走速直线逃离）：首次开火 0.28 秒、间隔稳定
**0.95 秒**、最高速度 240、最终距离从 500 缩到 119（真的追上了）。
回归测试 `EnemyChasesWalkingPlayerAndKeepsFiring`（对照实验：回退速度上限
修复后最高速度 145、断言失败 ✓ 有牙齿）。

仍然存在 2~5 秒的间隔，但那是**合法**的：玩家躲在掩体后、超出射程、或
视线被挡 —— 不再是"AI 站着不开枪"。

### 难度影响（需要你确认）

敌人射程 +25%、追击速度 +20%、走速 130→145，整体明显更难。
想回调只需改 `EnemyConfig::fireRange` / `sprintSpeed` / `moveSpeed`；
**改 `fireRange` 时记得同步 `defaultEnemyProjectile().maxRange`**，
否则一致性测试会失败（这正是它的用途）。

### 诚实说明：一处改动无法证明有效

`searchRearmDistance`（报告没变就不重新唤醒）我写了测试，但**回退该改动后
测试依然通过** —— 因为这些场景里队友赶到报点后通常立刻看见玩家、转入交战，
"反复唤醒"根本不发生（玩家无敌时实测它稳稳保持 196 距离射击，行为完全正常）。
因此我删掉了那条没有牙齿的测试，保留改动（语义上更正确、代价极低），
但把它记为**防御性改动**，而不是"修复了某个现象"。

## 三·补四：玩家射击「很怪 / 有时射不出来」（用户澄清后的真正修复）

上一轮我把"射击很怪"理解成了**敌人**的射击，修的是 AI 的枪。用户澄清后重新定位：
问题在**玩家**这一侧。两个真因，都用实测数据钉死。

### 1. 按下事件被"渲染帧对齐"整帧吞掉（主因）

链路：`Input::update()` 每**渲染帧**采样一次，而游戏逻辑在**固定步**里消费
（`SandboxLayer::onFixedUpdate`）。渲染帧率高于逻辑帧率时，有些渲染帧
根本没有逻辑步：

```
实测截图：frame 420 / 逻辑步 209        （120FPS，约一半帧没有逻辑步）
实测截图：frame 600 / 逻辑步 313
```

而原实现里"按下"只存活一帧：

```cpp
state.pressed = nowDown && !state.down;   // 下一帧重算时归零
```

于是落在"没有逻辑步"那一帧里的点击**整帧蒸发**——点击能不能变成子弹，
完全取决于它落在哪一帧。帧率越高丢得越多：60FPS 下几乎察觉不到，
144/240Hz 屏上就是"点了没反应、间隔时快时慢"。

**修复**：按下事件**锁存到被消费为止**（上限 8 帧，防"暂停很久之后补一枪"）。
`consumeKeyPressed / consumeMousePressed` 取走锁存；
`isKeyPressed / wasActionPressed` 这类**非消费**读取仍是严格帧内语义（有测试守）。

一并修好的同类问题：翻滚（空格）、重开（回车）、增兵（N）、调试开关、imgui 面板点击
——它们全都走 `consumeActionPressed`，全都有同样的丢失窗口。

**顺带发现并修掉一个"输入层根本无法被测试"的问题**：
`Input::update()` 里的失焦清空只由 `TACTICALAI_HEADLESS_TEST` 宏保护，而那个宏
**只加在测试目标上**（`tacticalai_engine` 是正式配置编译的）。测试环境里
`IsWindowFocused()` 恒为 false → 每帧 `clear()` → 注入的按键立刻被抹掉。
改为运行时判断 `IsWindowReady() && !IsWindowFocused()`：有窗口时行为一字不变，
无窗口（测试/无头）不再无谓清空。

### 2. 玩家开火冷却比人手点击还慢（次因）

`Player.h` 里原本写着：

> 取 0.15s ≈ 每秒 6.7 发，**比人类极限略快**，属于"感觉不到但拦得住"。

**方向算反了**：6.7 次/秒 **慢于**人类极限（约 8 次/秒），所以快速点击会被
这个"兜底"上限挡住 —— 冷却条明明在走、枪就是不出。

**对照实验（实测）**：以 0.117 秒间隔点击 86 次（约 8.6 次/秒）

| 玩家冷却 | 打出子弹 | 说明 |
|---|---|---|
| 0.15s（原值） | **43 发** | 正好一半被静默拒绝 |
| 0.10s（现值） | **86 发** | 每一次点击都成枪 |

改成 0.10s ≈ 10 次/秒：真正落在人类点击极限之上，恢复它"兜底而非限速"的定位。
理论射速上限 6.7 → 10 发/秒，但实际射速仍由玩家点击速度决定，上限只对异常输入生效。

### 契约没有被破坏

README 的"**被拒绝的请求不排队**"依然成立：冷却期内点击仍然会被 `Player` 拒绝。
锁存只保证"事件一定会被送到 `Player` 判定一次"，而不是随机消失 ——
两者是不同的问题（一个是事件丢失，一个是主动拒绝）。

### 新增测试（`tests/test_input.cpp`，7 条）

| 测试 | 防的是什么 | 对照实验（回退修复后） |
|---|---|---|
| `PressSurvivesFramesWithoutLogicStep` | 核心：没有逻辑步的帧吞掉按下 | **失败** ✓ |
| `MouseClickSurvivesFramesWithoutLogicStep` | 同上（鼠标） | **失败** ✓ |
| `HoldingAKeyDoesNotRepeatPresses` | 锁存不能变成连发（半自动语义） | **失败** ✓ |
| `HighFrameRateClicksAllBecomeShots` | 端到端：120FPS+60Hz 下每次点击都成枪 | **失败**（43/86）✓ |
| `LatchedPressIsConsumedOnlyOnce` | 同一事件不能被消费两次 | 护栏 |
| `LatchedPressExpiresWhenNobodyConsumesIt` | 暂停很久之后不能补触发 | 护栏 |
| `NonConsumingReadersStayFrameScoped` | 非消费读取的帧内语义不被污染 | 护栏 |

为了能测输入层，`Input` 增加了两个**默认不激活**的注入口
（`setKeyDownForTest` / `setMouseDownForTest`）：不调用时行为与没有它们时
完全一致，代价只有一次 bool 判断。

### 顺带值得知道的一处隐患（未改）

引擎/游戏层的 `#if !defined(TACTICALAI_HEADLESS_TEST)` 守卫**在测试构建里全部失效**，
因为该宏只加在测试目标上，而 `tacticalai_engine` 等库是按正式配置编译的。
目前没有测试构造 `Renderer`/`CjkFont`，所以没炸；一旦有测试碰到它们，
就会在无窗口环境下调用 GLFW/OpenGL。彻底解决需要给测试单独编译一份
无头引擎库（构建改动较大），建议后续单独排期。

## 三·补五：敌人对着"空位置"射击

用户现象：敌人朝着没有人的地方连开好几枪。

### 根因：开火用的是"记忆里的位置"，而"记得"被当成了"看得见"

```cpp
// AimAndFire：目标位置来自黑板
if (!resolveTargetPosition(blackboard_, targetPosition)) return Failure;
// ↑ 这个辅助函数读的是 kLastKnownPosition —— 敌人**记忆**中的玩家位置
```

玩家离开视野（绕到背后、退出视野距离、躲进掩体）之后：

1. `kLastKnownPosition` **停在原地**（它就是"最后看到的地方"）；
2. 感知的"确认目标"（`hasConfirmedTarget`）在 `memoryDuration`（默认 **6 秒**）
   内**仍然为真** —— 那正是"记忆"的定义；
3. 于是交战分支继续活着，敌人朝着那个空位置瞄准、开火。

**LoS 检查救不了它**：那个空点自己有视线（它当初就是"视线内"才被记下的），
`losQuery_(自己, 瞄准点)` 当然通过。

**实测（干净场景，玩家瞬移出视野）**：

| | 开火 | 其中对着空位 | 看不见目标仍开火 |
|---|---|---|---|
| 修复前 | 9 发 | **7 发** | **6 发**（连续 6 秒） |
| 修复后 | 2 发 | **0 发** | **0 发** |

真实示例关卡（玩家绕圈走位 60 秒）：修复前 31 发里 2 发打空（6.5%）——
比例低是因为掩体常常顺手挡住视线（LoS 检查偶然掩盖了这个 bug），
但只要玩家一离开视野锥就没有任何东西拦得住。

### 修复一：开火要求"目标此刻还得在"

新增 `EnemyConfig::fireTargetMaxAge = 0.15s`：距上次**真正看见**目标超过它就不开枪。

判据必须用 `kTimeSinceSeenEnemy`（由 `Perception::timeSinceLastSeen` 写入，
**只在真看见时归零**），不能用"确认目标"——否则等于没改。
（`docs/ROADMAP.md` 里其实早就记过这条坑，只是没人把它用到开火上。）

### 修复二：失联超过宽限期就离开交战分支

新增 `EnemyConfig::engageLostGrace = 0.5s`。原来交战分支的条件只看"有确认目标"，
而它在记忆期内一直为真，于是交战分支（优先级高于搜索）把敌人**钉在原地 6 秒**。
超过 0.5 秒交给搜索分支后，敌人会真的走过去看 —— 这也是"AI 会找人"的关键。

### 修复三（排查时挖出来的更深的 bug）：观察动作被无限重播

`updatePerception` 里用 `hasConfirmedTarget()` 判断"重新确认目标"，
而它在记忆期内一直为真，于是：

```
搜索分支：到达 → 观察 0.8 秒 → 放弃 (searchAbandoned_ = true)
下一步 updatePerception：因为"还记得"，searchAbandoned_ = false、到达时刻重置
→ 回到"到达 → 观察 → 放弃"……
```

敌人被**钉在最后已知位置无限重播观察动作**（实测原地站了 3.5 秒以上，
直到 6 秒记忆过期）—— 这正是"跑到 last location 点位发呆"更根本的来源。

现在判据换成"**此刻真的看见**"（`timeSinceLastSeen ≤ 0.05s`，留一点抖动容差）。
连带修好一处副作用：`lastSeenEnemyTime_` 的语义是"最近一次**看见**"，
World 用它当小队情报的时间戳 —— 在"只是还记得"时刷新它，等于把情报
一直标成"刚刚看到的"。

### 实测（同一场景，修复前后）

```
修复前：站在记忆点，3 秒内累计位移 ≈ 13 单位（原地重播观察）
修复后：到点扫视 0.8 秒 → 离开，3 秒内累计位移 300+ 单位
```

### 回归测试（3 条，均用对照实验验证有牙齿）

| 测试 | 断言 | 回退对应修复后 |
|---|---|---|
| `DoesNotFireAtRememberedPosition` | 玩家离开视野后一发都不许再开 | **失败** ✓ |
| `DropsEngageBranchSoonAfterLosingSight` | 失联 2 秒后不得仍停在交战状态 | **失败** ✓ |
| `LeavesLastKnownPositionAfterScanning` | 到点后必须动起来（累计位移 > 120） | **失败**（仅 13 单位）✓ |

### 顺带发现（未改，供你决定）

巡逻环是以**出生点**为圆心的（`patrolHome_`）。所以一个跑出去很远搜索过的敌人，
放弃之后会一路走回出生点附近巡逻；靠得近时表现为"在记忆点附近来回晃"
（实测最远只到 84 单位）。战术观感上"从当前位置继续巡逻"更自然 ——
但那属于行为设计调整，我没有擅自改。

## 三·补六：靠在墙边就"隐身"（顺带也免疫子弹）

用户现象：贴着墙站，敌人发现不到自己。

### 根因：视线与弹道用的是**被膨胀过的格子**，不是几何真相

```cpp
// 视线（World::makeLineOfSightQuery）—— 沿线段每半格采样，问格子可不可通行
// 子弹（World::projectileBlockedAt）—— 同样问格子可不可通行
```

而阻挡格是**膨胀过的近似**：`NavGrid::fillRect` 用矩形角点的 `floor` 填格，
障碍只要**压住某格的一部分**，整格就被标成阻挡。于是每个掩体的实际阻挡
范围比它看起来的样子向外多出 **0~32 单位**（取决于墙面落在格子内的位置）。

测例（也是我用来复现的那堵墙）：墙面在 **x=700**，而 700 落在格 21
（`[672,704]`）里 ⇒ 格 21 整格变阻挡 ⇒ 阻挡范围从 672 开始，
**比墙面胖了 28 个单位**。

玩家贴着墙面站（x=688，距墙 12 单位）正好在这个"膨胀区"里：

| 实测 | 修复前 | 修复后 |
|---|---|---|
| 贴墙(688)被看见 | **否** | **是** |
| 贴墙目标掉血 | **0**（子弹在离墙一格远的地方消失） | **18** |
| 隔墙(760)被看见 | 否 ✓ | 否 ✓ |
| 隔墙目标掉血 | 0 ✓ | 0 ✓ |

也就是说，靠墙实际上是**隐身 + 免疫子弹**的双重护盾，
而且这层护盾有 0~32 单位厚且看不见。

### 修复：视线与弹道改为**精确几何**

- 新增 `segmentIntersectsRect()`（slab 法）。
- `makeLineOfSightQuery`：直接问"这条线段有没有穿过某个障碍矩形"。
- `projectileBlockedAt`：直接问"这个点是否落在某个障碍矩形内"
  （子弹子步 ≤ 6 单位、掩体厚度 ≥ 40 单位，逐点判定不会漏检）。
- 导航网格**保持不变**：它仍然是寻路/站立的权威（实体需要身体间隙，
  那里就该用"膨胀"表示）。问题只是**不该拿它判视线和弹道**。

顺带修掉的两件事：

1. **子弹与视线的"幽灵墙"**：判定现在读的是**活着的实体**，而不是派生
   网格数据。障碍被移除后不再可能出现"看不见的墙仍然挡视线/挡子弹"。
2. **掩体判定的一致性**：EQS 的掩护度、感知的可见性、弹道是否被挡，
   现在用的是同一套几何 —— 不会再出现"AI 觉得这里有掩体、子弹却穿过去"。

**代价（需要你确认）**：掩体从"胖一圈"变成"所见即所得"。躲在墙后依然安全
（有测试守着），但**站在墙边不再有任何额外保护** —— 这本身就是你要的效果。
示例关卡的墙都 ≥ 40 单位厚，掩体感不会因此消失。

### 回归测试（2 条，均用对照实验验证有牙齿）

| 测试 | 断言 | 回退修复后 |
|---|---|---|
| `HuggingWallDoesNotHidePlayerButWallStillBlocksSight` | 贴墙可见 + 墙后不可见 | **失败** ✓ |
| `HitsTargetHuggingWallButNotThroughIt` | 贴墙能打中 + 墙后打不中 | **失败** ✓ |

性能：视线判定从"每 16 单位一次格子查询"变成"逐个障碍矩形求交"，
但障碍只有十来个；实测 AI 平均耗时 **0.003~0.004ms**，无回归。

## 三·补七：展示化改造（录制能力 + 无头修复 + 打包前的门面）

这一轮的目标不是"修 bug"，而是把项目从"代码存档"变成"能被看到、能被验证的作品"。

### 1. 新增：连续抓帧 + 自动演示 + GIF 工具链

| 新增 | 作用 |
|---|---|
| `--capture <目录>` | 连续导出渲染帧为 PNG 序列（`--shot` 只能拍一张，而"AI 在动"是时序行为） |
| `--capture-every <n>` | 每 N 个渲染帧一张（默认 4） |
| `--demo` | 内置驾驶员接管玩家：走位 / 瞄准 / 开火 / 躲弹翻滚，**并自动打开感知·EQS·路径可视化** |
| `src/game/AutoPilot.*` | 驾驶员本体（确定性策略，不含随机数；放在 game 层，和真人走同一条输入 API） |
| `scripts/make_gif.ps1` | PNG 序列 → MP4 → GIF（两遍调色板；体积经验值与参数说明写在脚本里） |
| `docs/RECORDING_GIF.md` | 录制手册：三步命令、参数怎么选、录什么、体积经验值、7 个坑 |

**为什么放在 game 层**：`AutoPilot` 写的是"玩家意图"（`setMoveIntent` / `setLookAtPoint` /
`requestFire` / `tryStartRoll`），与真人按键走完全相同的链路 —— 演示里看到的不是
"演示特供逻辑"。而且它不含随机数，因此同一条命令能复现同一段演示
（这正是"固定步长 + 确定性逻辑"的一次实际兑现）。

**抓帧的两个关键点**：必须在 `endFrame()` **之前**抓（之后 SwapBuffers 已发生，读到空帧），
且读像素前先 `rlDrawRenderBatchActive()` 强制 flush（否则抓不到 HUD）——与 `--shot` 同一套理由。

### 2. 修复：`scripts/fetch_dependencies.ps1` 在 Windows PowerShell 下无法运行

`.ps1` 文件没有 UTF-8 BOM，而 Windows PowerShell 5.1 对无 BOM 脚本按本地代码页
（中文环境是 GBK）解析 —— 该脚本含 48 行中文注释，会直接解析失败。
后果是 README 的第一条命令在"只装了 Windows PowerShell（没装 pwsh 7）"的机器上就断掉。

修法：给两个 `.ps1` 都加 UTF-8 BOM，并用 PowerShell 的解析器 API 校验语法为 0 错误。
（新脚本 `make_gif.ps1` 另外避开了两个坑：`$ErrorActionPreference = "Stop"` 会把
ffmpeg 写到 stderr 的警告升级成致命错误，改为显式检查 `$LASTEXITCODE`；
`$Colors:stats_mode` 会被解析成"驱动器变量"，写成 `${Colors}:stats_mode`。）

### 3. 修复：把"无头"从构建期宏改成运行期参数

**问题**：`TACTICALAI_HEADLESS_TEST` 只加在测试目标上，引擎库仍按正式配置编译 ——
引擎里所有 `#if !defined(TACTICALAI_HEADLESS_TEST)` 守卫在测试构建里**全是失效的**。
也就是说"我们有 279 个无头测试"这句话里，藏着一个随时会咬人的假设。

**修法**：`Renderer(int, int, string_view title, bool createWindow = true)`，
并把窗口调用的守卫统一改成运行期 `IsWindowReady()`：

- `createWindow = false`：不 InitWindow、不 LoadFontEx、不 LoadRenderTexture；
  `screenWidth()/screenHeight()` 返回构造时声明的尺寸；析构只关"自己创建的窗口"。
- 渲染纹理在没有窗口时保持 `valid_ = false`，`begin()/end()` 自然成为空操作。

**对照实验（证据）**：`tests/test_renderer_headless.cpp`

```
传 createWindow = false  →  cjkFontLoaded = 0, RenderTarget::isValid = 0   （完全没做 GL 工作）
传 createWindow = true   →  fontLoaded = 1, renderTargetValid = 1，耗时 262ms
```

即修复前在单元测试里构造 `Renderer` 会**真的开窗、烘字体、建纹理** ——
在没有显示设备的 CI 上就是 UB。

## 四、已知未修（不影响"能玩"，供后续排期）
