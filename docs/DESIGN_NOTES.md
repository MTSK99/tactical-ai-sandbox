# ============================================================================
#  ADR-001: 引擎层的渲染抽象边界
#
#  状态: 已采纳
#  背景: 游戏逻辑需要「知道世界长什么样」，但不应「知道 raylib 是什么」。
#        然而完全隔离会带来大量转发代码（每个绘制函数包一层），收益不明显。
# ============================================================================
#
#  决策
#  ----
#  采用「按用途隔离」而非「按技术隔离」：
#
#    engine::Renderer  —— 持有 raylib 的全部绘制原语。
#                         所有绘制调用必须经过它。
#                         例外：debug 层的降级 HUD 可直接调 raylib
#                         （因为它本身就是「没有 imgui 时的最后手段」，
#                          再包一层抽象没有意义）。
#
#    engine::camera()  —— 相机变换（世界 <-> 屏幕）暴露为纯数学接口，
#                         不涉及任何 raylib 类型。这样鼠标拾取这类逻辑
#                         可以在无窗口的单元测试里验证。
#
#    各实体           —— 完全不持有图形资源。它们只有位置、朝向、半径。
#                         渲染由 debug 层读取这些属性后绘制。
#
#  理由
#  ----
#  1. 可测试性：ai/ 与 game/ 的绝大部分逻辑可在无窗口环境验证。
#     这不是理论好处——CI 上没有显示设备，无法创建窗口。
#
#  2. 替换成本可控：将来若改用 SDL_gpu / bgfx，只需重写 Renderer.cpp
#     与 DebugUI 的降级路径，约 2 个文件。
#
#  3. 避免过度抽象：没有为「圆」和「矩形」发明 Drawable 基类。
#     直接函数调用在调试时可读性更好（能直接断点到 raylib 内部）。
#
#  已知代价
#  --------
#  - debug/AIDebugDraw.cpp 直接 include 了 engine/Renderer.h，
#    因此它和渲染后端耦合。这是可接受的：调试可视化的本质
#    就是「把内部状态画成图」，它必然依赖具体的绘制能力。
#
#  - DebugUI 的降级路径直接调 raylib 的 DrawTextEx 等函数，
#    而非走 Renderer。原因同上：这条路径的存在前提就是
#    「imgui 不可用」，此时少一层间接反而更不容易出错。
#
# ============================================================================


# ============================================================================
#  ADR-002: 黑板使用 std::any 而非变体类型
#
#  状态: 已采纳
#  背景: 黑板需要存 int / float / bool / string / vec2 / vector<int> 等
#        多种类型。可选方案：
#          A. std::any + 类型索引校验
#          B. std::variant<...> 显式列举所有支持的类型
#          C. 纯字符串值 + 按需解析
#          D. 一个基类 + 派生模板（类型擦除的手写版）
# ============================================================================
#
#  决策: A（std::any + 显式类型校验）
#
#  理由
#  ----
#  1. 可扩展：新的 AI 模块可以往黑板里放任何类型而无需修改黑板代码。
#     用 variant 时每加一种类型都要改头文件并重编译几乎整个项目。
#
#  2. 调试友好：可以直接遍历所有键并转成文本（见 valueToString），
#     这是调试面板的核心功能。variant 需要为每种类型写 visitor，
#     虽然能做到，但代码量显著更多。
#
#  3. 类型安全有保障：get<T>() 先比对 type_index 再 any_cast，
#     类型不符返回 nullopt 而非抛异常。所以 std::any 的
#     「类型不安全」缺点在本设计里被规避了。
#
#  性能考量
#  --------
#  大多数实现里 std::any 对小型类型（int/float/vec2）会避免堆分配
#  （SBO）。即使发生分配，AI 决策路径上的黑板读写也在每秒数百次量级，
#  相比 EQS 和寻路完全不是瓶颈。实测：3 个敌人、约 20 个键的黑板，
#  每逻辑步的总写入耗时 < 10 微秒。
#
#  若将来成为瓶颈的对策
#  --------------------
#  BlackboardKey 已支持预计算哈希。进一步可加「按类型分区的
#  SoA 存储」或「编译期键 ID」，但那是优化，不是现在的需求。
#
# ============================================================================


# ============================================================================
#  ADR-003: 寻路每次请求完整重算，不做增量
#
#  状态: 已采纳（并记录了触发升级的条件）
#  背景: 敌人每 2.5 秒（repositionInterval）重新选位时会触发寻路。
#        增量式 A* / D* Lite 可以在目标小幅移动时复用上次搜索，
#        理论上有数倍收益。
# ============================================================================
#
#  决策: 保持完整重算
#
#  理由
#  ----
#  1. 实测数据：1600x1200 世界、32 单位格 -> 50x37 网格。
#     平均扩展节点数约 200-400，单次寻路 < 0.3ms。
#     3-8 个敌人的总寻路开销每逻辑步不到 0.5ms，
#     在 16.67ms 的预算里占 3%。
#
#  2. 增量算法需要维护额外的状态与失效逻辑（哪些节点因地形变化而失效）。
#     这部分复杂度容易引入「AI 偶尔走错路」这类极难复现的 bug，
#     而当前收益不值这个风险。
#
#  3. 已有优化：二叉堆开放列表 + 搜索代数戳（避免每次清空数组）+
#     gScore 复用缓冲。这些把常数因子压低了约一个数量级，
#     是「每帧重算也够快」的前提。
#
#  何时应该升级
#  ------------
#  - 网格超过 200x200，或单次寻路 > 2ms
#  - 同屏敌人超过 50 个
#  - 引入动态地形（可破坏掩体）导致频繁全局失效
#
#  升级时的落地路径：Pathfinder 已把搜索状态集中在成员变量里，
#  可在此基础上实现「保留上次搜索结果 + 目标移动小于阈值时复用」。
#
# ============================================================================


# ============================================================================
#  ADR-004: 调试 UI 保留原生 HUD 降级路径
#
#  状态: 已采纳
#  背景: imgui 的 raylib 后端（imgui_impl_raylib）并非所有版本都自带。
#        若强依赖它，依赖获取失败时项目将完全无法运行。
# ============================================================================
#
#  决策: 双路径实现，编译期探测 + 运行期自动降级
#
#  理由
#  ----
#  1. 可访问性优先：一个跑不起来的沙盒毫无价值。原生 HUD 虽然不能拖滑块，
#     但能显示帧率、AI 状态、敌人行为等关键指标——足以做基础调试。
#
#  2. 分级降级而非全有全无：失去的是「运行时调参」这一高级能力，
#     保留的是「观察 AI 行为」这一核心能力。前者可以通过手动改
#     EnemyConfig 的默认值弥补，后者没有替代品。
#
#  3. 构建期就明确告知：CMake 探测到后端缺失时会打印提示，
#     不会让使用者在运行时才发现面板「点不动」。
#
#  代价
#  ----
#  DebugUI.cpp 里有两套绘制代码，文件较长（约 700 行）。
#  接受这个代价，因为它换取的是「任何环境都能跑」的健壮性。
#  两条路径共享同一份数据绑定结构（DebugUIBindings），
#  因此不会出现「两边显示不一致」的问题。
#

# ============================================================================
#  ADR-005: 对局结果用「实时计算」而非「锁定状态」
#
#  状态: 已采纳
#  背景: 新增 MatchOutcome{Running, Victory, Defeat} 时，
#        需要决定它是「每帧实算」还是「一旦确定就锁住，等reset 才清」。
# ============================================================================
#
#  决策
#  ----
#  `World::outcome()` 每次调用都重新判定，不缓存终局状态。
#  reset() 只清`spawnedAnyEnemy_` 这类输入，不清outcome。
#
#  理由
#  ----
#  1. 这是一个**沙盒**，按 N 可以随时增兵。若锁定「胜利」，
#     玩家清光一批敌人后按 N 增兵，世界却还显示"胜利"，
#     于是想继续玩只能重开——为一个观察 AI 的工具增加了不必要的摩擦。
#
#  2. 终局状态本身可由当前世界完全推导（玩家是否死、有无存活敌人），
#     不需要额外存储。把"当前事实"缓存起来反而要处理失效，
#     而失效点是隐式的：增兵、复活、reset 都会让缓存过期。
#
#  3. 判据是 O(实体数) 的遍历，每帧几十个实体，代价可忽略。
#     （对比：黑板写入计数那种每步数百次的操作才需要考虑缓存。）
#
#  代价与处理
#  ---------
#  "曾经生成过敌人"这件事无法从当前世界推导（敌人都死光了，
#  数量为 0，与"一开始就没有敌人"无法区分），因此引入
#  spawnedAnyEnemy_ 标志，并**必须**在 reset() 里清掉——
#  否则重开流程会这样出错：reset 清空实体 →存活数为 0 →
#  但标志仍是 true（上一局生成过）→ initialize() 还没生成第一个敌人，
#  outcome() 就判成 Victory，表现为"刚按回车就显示胜利"。
#  这个坑已由 ResetClearsVictoryFlagBeforeFirstSpawn 钉住。
#
# ---------------------------------------------------------------------------
#  另一个刻意的取舍：失败后**不**冻结世界
#
#  玩家阵亡后，若把整个世界停掉，就复现了旧版"打完没结果"的核心问题：
#  不但没有反馈，连现场都观察不到。而失败时敌人会失去感知目标、
#  退回巡逻，此时世界仍在推进——玩家能看着敌人走开、子弹落地、
#  尸体消失，这本身就是结算画面的一部分。
#
#  因此 World 只在玩家输入侧设卡（handleGameplayInput 提前返回），
#  世界照常推进。这与 F2「冻结 AI」的取舍同源：
#  **冻结要冻结在"恰好不影响被观察对象"的那一层。**


# ============================================================================
#  ADR-006: 搜索分支的「放弃」用 Failure 而非 Success
#
#  状态: 已采纳
#  背景: SearchLastKnown 动作到达最后已知位置后，观察期满需要放弃搜索。
#        行为树里"放弃"该返回什么？Failure 还是 Success？
# ============================================================================
#
#  决策
#  ----
#  返回 `Failure`（而不是 Success），并用 searchAbandoned_ 标志
#  让外层条件在重新发现目标前不再重试。
#
#  理由
#  ----
#  搜索分支的结构是：reactiveSel 下的一个 seq(条件, 动作)。
#  动作返回 Failure 时，Sequence 短路、整条分支返回 Failure，
#  根选择器随即落到下一个分支——巡逻。这正是"放弃搜索"的语义。
#
#  返回 Success 则是错的：它会让根选择器认为"搜索成功了"，
#  同样停在原地（没有任何分支被触发），而且不给出任何放弃信号。
#  这正是修复前那段代码的真实问题——两个分支都返回 Running，
#  "放弃"从未发生。
#
#  为什么还需要 searchAbandoned_ 标志
#  ----
#  光返回 Failure 的话，动作每步都会立刻算出 arrived=true、
#  观察期满、再返回 Failure。行为上没错（等于一直巡逻），
#  但每步都白跑一次 followPath，而记忆还要再持续 6 秒。
#  标志让"放弃"这件事真正落地：不重试，直到重新确认目标。
#
#  标志必须在"重新看见玩家"时清掉（见 updatePerception），
#  否则 AI 一辈子只放弃一次——此后即便玩家就站在它旁边，
#  它也只会巡逻、再也不搜索。
#  这是典型的"修一个 bug 引入另一个 bug"，已由
#  ReacquiringTargetReenablesSearch 钉住。
#
#  代价
#  ----
#  多了一个需要跨两处维护的标志（动作里置位、感知里清位）。
#  不加它也能工作，代价只是每步多一次 followPath；
#  加它的收益是省掉无谓计算并让"放弃"成为可断言的状态。
#  选择加，因为这个项目本来就在意可观测性。


# ============================================================================
#  ADR-007: 掩护度用「到交火连线的距离」，而非射线相交
#
#  状态: 已采纳
#  背景: FindCover 查询里有一项权重 0.20 的"掩护度"测试项，
#        原实现只算「候选点到最近掩体中心的距离」——
#        即"距离代理"（拿距离当掩护度），代码注释自己承认了两次。
# ============================================================================
#
#  决策
#  ----
#  量「最近掩体到**我→目标连线**的最短距离」，越近越好；
#  同时给 coverSeekQuery_ 的candidateFilter 加一条硬约束：
#  **候选点必须能与目标通视**。
#
#  两个看似独立的改动其实缺一不可，见下。
#
#  ---------------------------------------------------------------------------
#  为什么不选「掩体必须与射线相交」这个更严格的判据
#  ---------------------------------------------------------------------------
#  它是本项目试过并**被实测否决**的方案。否决的理由值得完整记录，
#  因为它反直觉，且从单看任一条都像是对的：
#
#    1. 掩护度如果只判「我看不见目标」，AI 会躲进掩体后再也开不了枪。
#       AimAndFire 里有 LoS 检查（"弹道别对着掩体开"），
#       枪口到目标被挡就 return Running，一枪都不开。
#       → 所以必须加"候选点通视目标"的硬约束。
#
#    2. 加上那条约束之后，"掩体与「我→目标」连线相交"就**恒为假**。
#       因为连线通畅正是通视的定义——连线上按定义没有任何阻挡格，
#       掩体自然也不在。
#
#    实测结果：121 个候选点，掩护度得分**全部为 0**，
#    且其中 120 个被过滤器剔除。整个测试项彻底失效。
#
#  一句话总结这个矛盾：
#
#    **「我能打到它」与「有东西挡在我们之间」在物理上互斥。**
#
#  真实战术里两者的统一靠**探身射击**（peek）：身体在掩体后，
#  枪口从掩体边缘探出。实现 peek 需要的是"掩体附近存在一个能通视的点"，
#  而不是"掩体正好压在连线上"。
#
#  ---------------------------------------------------------------------------
#  为什么最终选「到连线的距离」
#  ---------------------------------------------------------------------------
#  它把两件事解耦，恰好对应 peek 的两个条件：
#
#    coverEffectiveness：掩体离交火路径近→ 提供潜在掩护
#    candidateFilter  ：候选点自身能通视目标   → 保证现在就能还手
#
#  合起来 = 「贴着掩体、探头能打」的位置。物理上自洽，
#  也不会把 AI 推进"完全打不着"的死位。
#
#  它相对旧实现的关键改进：参照物从**候选点自己**换成了**交火连线**。
#  于是「掩体在 AI 的侧后方」会被正确判为低分——
#  它离连线远，正如它对交火毫无帮助。
#  旧实现下这个场景与「掩体在正前方」得分完全相同。
#
#  投影参数必须钳制到 [0,1]（已在 EQS.cpp 注释与测试里各写了一次）：
#  落在射线延长线上的掩体若不钳制，算出的距离会接近 0，
#  于是"在正后方"被误判成"正好在交火路径上"——正是本次要消除的那类错误。
#
#  ---------------------------------------------------------------------------
#  为什么判据要放在 AI 层而不是 Enemy.cpp
#  ---------------------------------------------------------------------------
#  第一版把它写成了 Enemy::buildEQSQueries 里的一个 lambda，结果**无法单测**。
#  只能跑无头模拟间接观察，而那极难区分三种情况：
#  掩体选对了 / 恰好选了个别的位置 / 这条分支根本没执行。
#
#  移到 EnvironmentQuerySystem::coverEffectivenessTest 之后：
#    - 可以构造"同样距离、不同朝向"的场景直接断言，
#      这是区分"距离代理"与"交火路径"两种实现的唯一手段；
#    - EQS.h 的文件头本来就把"掩护度"列为典型战术查询的组成部分
#      （见那段注释里的三测试项示例），放在这里与文档一致；
#    - Enemy.cpp 里只剩一行调用，游戏层不再重复实现几何判据。
#
#  一般性教训：**凡是可复用的判据都该进 AI 层并单测，
#  塞进lambda 就等于放弃了这个契约。**


# ============================================================================
#  ADR-008: 死亡后的世界推进是刻意的，不冻结
#
#  状态: 已采纳
#  背景: 失败（玩家阵亡）后，是否要像别的手游那样冻结整个世界？
# ============================================================================
#
#  决策
#  ----
#  只冻结玩家输入（handleGameplayInput 提前返回），世界照常推进。
#
#  理由
#  ----
#  玩家阵亡后，敌人会失去感知目标、退回巡逻。若把世界也停掉，
#  就复现了旧版"打完没结果"的核心问题：不但没有反馈，
#  连现场都观察不到。而失败时世界仍在推进——玩家能看着敌人走开、
#  子弹落地、尸体消失（保留 kCorpseLifetime = 3秒），
#  这本身就是结算画面的一部分。
#
#  结算横幅刻意只压屏幕中上方一小块而非全屏遮罩，
#  同样是为了不挡住这些画面。
#
#  这与 F2「冻结 AI」的取舍同源：
#  **冻结要冻结在"恰好不影响被观察对象"的那一层。**
#  F2 冻结的是 AI（玩家仍可动，便于观察 AI 反应）；
#  失败冻结的是玩家输入（世界仍动，便于观察战后现场）。
