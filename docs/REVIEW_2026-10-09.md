## A. 上一轮改动的遗留与回归（优先修）

### A1【高｜我引入的回归】撤退分支读错黑板键 → 低血量敌人朝玩家冲

`src/game/Enemy.cpp:399-413`，配合 `src/game/Enemy.cpp:51-58`

```cpp
inline bool resolveTargetPosition(const AI::Blackboard& blackboard, glm::vec2& out) {
    if (const auto lastKnown =
            blackboard.get<glm::vec2>(AI::Blackboard::Keys::kLastKnownPosition)) {  // ← 读的是"玩家最后已知位置"
```

```cpp
// MoveToRetreat
glm::vec2 destination;
if (!resolveTargetPosition(blackboard_, destination)) { destination = moveTarget_; }
// 【修复】...注释说"优先取黑板里的 kMoveTarget"——但实际不是
const bool arrived = followPath(context.fixedDelta, destination);
```

`FindRetreatPosition` 写入撤退点用的是 `kMoveTarget`（`Enemy.cpp:389/493/506`），而 `resolveTargetPosition` 读的是 `kLastKnownPosition`。由于"见过玩家"之后这个键几乎恒存在，`destination` = 玩家方向。
**后果**：低血量敌人会主动冲向玩家，撤退机制形同虚设。
**是我上轮"消除死变量"造成的**：上一版用 `moveTarget_`（恰好正确），我改成 `destination` 时误信了那个辅助函数的语义。

**修**：`followPath(context.fixedDelta, moveTarget_)`，或让辅助函数显式读 `kMoveTarget` 并重命名为 `resolveMoveTarget()`（当前名字太容易被误读）。
**必须补测试**：撤退时"移动目标到威胁源的距离 > 当前位置到威胁源的距离"。

### A2【高｜我引入的副作用】AI 冻结期间敌人无限连发

`src/game/World.cpp:711-733`、`856-885`；清零点只在 `src/game/Enemy.cpp:770`

```cpp
// World：AI 冻结分支只清速度
for (const auto& entity : entities_) {
    if (entity->type() == EntityType::Enemy) entity->setVelocity({0.0f, 0.0f});
}
...

```

```cpp

```

冻结时 `updateAI` 不再被调用，于是**冻结前一帧开过火的敌人会永久保持 `firedThisStep_ == true`**，每逻辑步生成一颗子弹，且冷却判定（在行为树内）同样被跳过。按 F2 想"静帧观察"，得到的是无限机枪。

**修**：给 Enemy 加 `clearStepIntent()`（清 `firedThisStep_`/`aimSteeredThisStep_`），World 在冻结分支里调用；更彻底的做法是把"本步意图"的所有权移到 World 的两个阶段（收集意图 → 统一施加），因为 `updateAI` 之外的代码路径（比如未来加"脚本化 AI"）同样会踩这个坑。

### A3【中｜我上轮的"修复"是空操作】`Input::clear()` 没解决问题，而且没人调用

`src/engine/Input.cpp:274-290`

```cpp
    lastMousePosition_ = mousePosition_;   // clear() 内
```

`update()` 末尾本来就是 `mousePosition_ = GetMousePosition(); mouseDelta_ = pos - last; lastMousePosition_ = pos;`（`Input.cpp:260-266`），所以这两者**本来就相等**，这行等价于 no-op。恢复焦点第一帧的巨量 delta 依然存在（窗口失焦期间的真实鼠标位移差）。

更关键的是：全项目**没有任何地方调用 `clear()`**（头注释却写着"窗口失焦、场景切换时调用"）。alt-tab 后的卡键问题从未被处理。

**修**：在 Input 内部加焦点生命周期——`update()` 里检测 `!IsWindowFocused()`，失焦帧直接 `clear()` 并跳过差分；`clear()` 里用 `GetMousePosition()` 重新采样而不是复制旧值。

## B. 新代码的正确性问题

### B1【高｜已复核】`processWeaponFire` 在遍历 `entities_` 时插入实体（UB）

`src/game/World.cpp:865-885`，插入点 `src/game/World.cpp:438`

```cpp
for (const auto& entity : entities_) {          // 865：range-for 缓存 begin/end 与引用
    ...
    (void)spawnProjectile(...);                 // 881 → entities_.push_back(...)
}
```

`World` 构造函数只 reserve 了 `perceptionTargets_/threatSources_/coverPositions_/damageEvents_/impactMarks_`（`World.cpp:38-42`），**没有 reserve `entities_`**。一旦某步有敌人开火、且 push 触发扩容，`entity` 引用与迭代器全部悬垂 → 随机崩溃或"这一步某个敌人没开火"。交火越密越容易命中，属于典型的"平时看不出来"。
**修**：先把开火意图收集到局部 `std::vector`，循环结束后统一 `spawnProjectile`；同时给 `entities_` 一个初始 reserve（治标）。这也和 `World.h:11-13` 的"外部只拿 ID / 短期指针"的声明保持一致——头注释应补一句"步进期间不得增删实体，增删走延迟队列"。

### B2【中｜已复核】`isPositionWalkable` 把越界邻格 `continue` 掉，与注释相反

`src/game/World.cpp:614-620`

```cpp
const AI::GridCoord probe{center.x + dx, center.y + dy};
// 越界视为阻挡：地图边界外没有可站立空间。
if (!navGrid_.inBounds(probe) || navGrid_.isWalkable(probe)) {
    continue;                       // ← 越界被"跳过"，而不是判阻挡
}
```

`NavGrid::isWalkable` 对越界格本来就返回 false（越界 → `kBlocked`）。这里的 `!inBounds` 短路让"圆心在图内、半径伸出图外"的点**漏过 AABB 判定**而返回可站立。`contains(position)` 只拦圆心（`World.cpp:578`），拦不住半径。
**修**：删掉 `!inBounds(probe) ||`，让越界格走 AABB 判定被 reject；或显式 `return false`。
**测试缺口**：`test_walkable.cpp:154-161` 只测了"圆心越界"，没测"圆伸出地图"——正好是漏洞所在。

### B3【中｜已复核】碰撞退化分支用未归一化法线投影速度 → 速度爆炸

`src/game/World.cpp:1153-1187`

```cpp
if (distance < 1e-4f) { ... position.x = center.x - half.x - radius; ... }  // 已把实体推到矩形外
...
const glm::vec2 normal = (vectorLength(offset) > 1e-4f)
                             ? offset / vectorLength(offset)
                             : glm::vec2(position.x - center.x, position.y - center.y);  // ← 模长 = half + radius
const float intoWall = velocity.x * normal.x + velocity.y * normal.y;   // ≈ 800·|v|
if (intoWall < 0.0f) entity.setVelocity(velocity - normal * intoWall);  // ≈ 6.4e5·|v|
```

退化分支（实体中心落在障碍矩形内部）里回退法线的模长是"半宽/半高 + 半径"，长墙可达数百 → 速度被放大 2~3 个数量级，表现为贴墙抖动/弹飞。
**修**：退化分支按最短轴构造**单位**法线（±x / ±y），不要拿位置差向量当法线。顺带把 `minPenetration == dxLeft` 这类浮点相等比较改成"取 argmin"。

### B4【中｜已复核】`removeEntity` 删障碍物不解除导航网格阻挡 → 幽灵墙

`src/game/World.cpp:478-489`（只清了 `coverPositions_`）vs `src/game/World.cpp:409`（spawn 时 `navGrid_.fillRect(..., true)`）

全项目没有任何 `fillRect(..., false)` / `setBlocked(..., false)`。障碍被移除后：AI 会绕一块"看不见的墙"、`isPositionWalkable` 判不可站立、子弹被虚无地形挡住（`projectileBlockedAt` 用的就是 `navGrid_`）。
现在唯一调用方只删敌人（`main.cpp` 的"清空所有敌人"），所以是潜在缺陷；但 `removeEntity` 是公开 API，且作者已经为 `coverPositions_` 补了同步逻辑，说明"派生状态要跟着走"是既定意图——**漏掉的这一份比 coverPositions_ 更关键**。
**修**：障碍分支补 `navGrid_.fillRect(min,max,false)` + `computeClearanceField()`；更稳的做法是让导航网格由实体列表派生（`rebuildNavGrid()`），一次性消灭这类同步问题（同类的还有 `coverPositions_`、`threatSources_`、`enemyCount_`）。

### B5【中｜已复核】`reset()` 的 `elapsedGameTime_` 归零是假的

`src/game/World.cpp:121`（reset 置 0）vs `src/game/World.cpp:678`（update 无条件覆盖）

```cpp
elapsedGameTime_ = gameTime;   // 外部时钟的绝对时间
```

重开后跑一步就恢复成上一局的绝对时间，HUD 的 `t=%.1fs` 继续显示旧值。
**测试给了错误信心**：`test_match_outcome.cpp:252` 断言 reset 后为 0，但它在 reset 之后**没有 step**，所以刚好通过。
**修**：记 `matchStartGameTime_`，`elapsedGameTime_ = gameTime - matchStartGameTime_`；测试补"reset 后再跑 60 步，时间仍从 0 开始"。

### B6【中｜已复核】`outcome()` 与尸体/残弹的交互

`src/game/World.cpp:249-270`，调用点 `src/main.cpp:396`

- Victory 判据是 `spawnedAnyEnemy_ && aliveEnemyCount() == 0`，**不等尸体队列、不等在空的敌方子弹**：最后一击后死者的残留子弹仍可能命中玩家，下一帧 `Defeat` 优先，于是"胜利横幅"翻成失败。
- 调试面板"清空所有敌人"直接 `removeEntity` → 一次没打就 `Victory`（`kills=0`）。

**建议**：引入"决胜锁定"（首次判定即固定）或 Victory 附加条件（无在飞敌方子弹 && `pendingRemoval_` 为空）；把 `outcome()` 的实时语义写进头注释并加测试。

### B7【中｜已复核】`enemies()` 的语义与文档相反

`src/game/World.h:184-186` 写的是"所有存活的敌人"，实现（`World.cpp:228-237`）只按类型过滤、**不过滤 `isDead()`**，而尸体会滞留 3 秒。`enemyCount_` 实为"本局曾生成总数"，HUD 的"存活敌人: 0 / 3"分母因此对不上标签。
**修**：拆成 `allEnemies()` / `livingEnemies()`；`enemyCount_` 改名 `spawnedEnemyTotal_`。

### B8【中｜已复核】敌人 `state_` 与行为树分支可能不一致

`src/game/Enemy.cpp:437-511`（交战选位）、`:605`（只在真正开火时 `setState(Engaging)`）

`state_` 由"最后一个动作调用的 setState"决定：从巡逻切入交战时首枪之前仍是 `Patrolling`；冷却中/瞄不准返回 Running 时也不刷新；EQS 选位后可能残留 `Repositioning`。`test_enemy_search.cpp:345` 已经用 `Engaging || Repositioning` 兜底，说明边界模糊已被感知。
**建议**：状态由"当前 Running 的分支"派生，或在分支入口统一 `setState`。

### B9【中｜已复核】`hasLastKnownPosition_` 永不失效 → EQS 幽灵目标

`src/game/Enemy.cpp:817-820`（只置 true，无任何置 false）；`:849-852`

```cpp

```

一旦见过敌人就永久为真，放弃搜索转入巡逻后，EQS 仍以过期坐标为中心布点/评分。
**修**：用记忆窗口门控（`gameTime - lastSeenEnemyTime_ < searchDuration` 或 `perception.memoryDuration`）。

### B10【中｜已复核】EQS 三处健壮性

- **NaN 未防护**：`src/ai/EQS.cpp:32` `std::clamp((raw-rangeMin)/span,0,1)` 对 NaN 仍返回 NaN → `candidate.score = NaN`；`score < minAcceptableScore` 对 NaN 恒 false（不会被剔除），随后 `stable_sort` 的比较器失去严格弱序 → **UB**。建议在 `measure` 之后 `if (!std::isfinite(raw)) return 0.0f;`。
- **候选数量无上限**：`src/ai/EQS.cpp:59-89`，`radius=2000, spacing=1` 时 `reserve` 约 1600 万点。建议加 `kMaxCandidates`（如 4096）并截断告警。
- **"固定种子"注释与实现矛盾**：`src/ai/EQS.cpp:73-74` 说"固定种子保证确定性"，种子却含 `gameTime`（点集随时间变）；`double→uint32_t` 强转在 gameTime 极大时是 UB。现有测试只测"相同 gameTime 确定"，恰好绕过。

### B11【中｜已复核】`main` 的三处用户可见问题

- **暂停后相机不能拖拽/缩放**：`updateCamera` 只在 `onFixedUpdate` 里调用（`main.cpp:398`），暂停/慢动作时固定步不产生 → 中键平移与滚轮缩放全失效。与"暂停观察现场"的设计意图冲突。建议把平移/缩放移到 `onVariableUpdate`（玩家跟随留在固定步）。
- **`--shot` 默认帧号退化成第 0 帧**：`main.cpp:334-336` 的 `std::max(options.maxFrames - 1, 0)`，在没给 `--frames` 时 = 0，而帧计数从 0 开始 → 第一帧（几乎空白）就截图，与注释"取最后一帧"相反。
- **`--shot` 文案说"截图后退出"但代码不退出**（`main.cpp:109/153` vs 主循环退出条件），只给 `--shot` 会一直跑到手动关窗。

## C. 测试质量问题（"看起来在测、其实没测"）

### C1【高｜已复核】DPS 上界断言被玩家血量封顶，恒真

`tests/test_combat_cooldown.cpp:291-317`

`totalDamageDealt_` 只在命中且 `dealt > 0` 时累加，而玩家只有 100 血、死后伤害恒为 0 → 20 秒内总量 ≤ 100，`perEnemyDps ≤ 100/20/3 ≈ 1.67 < 12` **永远成立**。也就是说：即使冷却完全没接线（原始 bug 的 240 DPS），这条断言照样绿。
**修**：同文件 `ShorterCooldownProducesStrictlyMoreShots` 的做法——先把玩家设成不可死（`setMaxHealth(1e6)`/`setHealth(1e6)`）再算 DPS。

### C2【中｜已复核】`ResetRestoresStatistics` 没有"先非零"前置

`tests/test_match_outcome.cpp:239-253`：`killPlayer` 走 `applyDamage`，不累加射击/伤害统计；随后只 step 0.5 秒（敌人冷却 0.95s）几乎不可能开火 → reset 前这些量本就是 0，断言 reset 后为 0 是同义反复。
**修**：reset 前先制造一次开火并 `ASSERT_GT(totalShotsFired(), 0u)`，再验证清零。

### C3【中｜已复核】`WorldKeepsSimulatingAfterDefeat` 的断言是弱代理

`tests/test_match_outcome.cpp:140-142` 断言 `elapsedGameTime() > 0`，而该字段就是 `step()` 自己传入的 gameTime（`World.cpp:678` 无条件赋值）→ 只证明"我调用了 update 60 次"，与仿真是否推进无关。
**修**：断言失败后敌人仍在移动/状态仍在变化（例如"最远位移 > 1 单位"）。

### C4【中｜已复核】`ProjectileCountDropsBackToZeroAfterFirefight` 的"持续交火"设定无效

`tests/test_projectile.cpp:433-439`：玩家在 `(400,600)` 朝 +x 射击，6 个"靶子"却在 `y=200`（不在弹道上），且 `makeTrainingDummy` 让它们不开火 → 注释所称"持续交火"不存在，这些敌人是死代码（结论仍成立，但理由不成立）。

1. **`setAIEnabled` 零覆盖** → A2（冻结无限连发）至今没有任何测试能发现。建议：冻结 → 步进 60 帧 → 断言 `totalShotsFired()` 不增长。

3. **重开残留**：反复 reset 后 `coverPositions_`/`navGrid_`/`aiEnabled_`/`impactMarks_` 是否翻倍或残留——正是刚修过的同类 bug，没有回归测试防复发。
4. **撤退分支零覆盖** → A1 就藏在这里：没有任何测试断言"低血量时目标应远离威胁源"。
5. **状态机迁移**（Patrolling→Engaging→Repositioning→Retreating→Dead）零断言 → B8 长期隐形。
6. **`enemies()` 是否含尸体**、**显式位置 spawn 的合法性**、**`snapToWalkable` 无解路径**、**`outcome()` 的残弹/尸体边界**均无用例。
7. **`Input` 完全没有单元测试**（键位状态机、consume 语义、`clear()`、焦点处理）。
8. **EQS**：`measure` 返回 NaN/∞、生成器候选上限、不同 gameTime 改变抖动点集、`distanceFromTargetTest` 无目标应得满分——均未覆盖。

## D. 架构 / 可维护性建议

1. **"派生状态多处维护"是这个世界最主要的架构气味**：`navGrid_`、`coverPositions_`、`threatSources_`、`enemyCount_`、`spawnedAnyEnemy_`、`Player::damageDealt_`、`Enemy::damageDealt_`、`totalDamageDealt_` 都是同一批事实的副本，每加一个写入点就要在多处同步（B4/B5/B7 全是这个模式的不同表现）。
   建议：导航网格改为 `rebuildNavGrid()`；掩体/威胁列表只由 `collectThreatSources()` 生成（删掉 `spawnObstacle` 的 push 与 `removeEntity` 的 erase）；统计量分"本局累计"与"个体数据"两层。
2. **步语义应由 World 定义**：`firedThisStep_`、`aimSteeredThisStep_` 这类"本步标志"目前由 Enemy 私有维护，只有在 `updateAI` 被调用时才正确（A2 就是后果）。建议统一 `resetStepIntent()` 钩子，或改成 World 侧的两段式（收集意图 → 统一施加)。
3. **`World::update` 的 7 个阶段应写成文档**（清事件 → 收集 → AI → 开火 → 子弹 → 回收子弹 → 积分 → 约束 → 回收尸体），现在散落在 6 处注释里；下一个人加"近战"极易插错位置。
4. **`Enemy` 是 God class**：约 40 个成员，`buildBehaviorTree()` 单函数约 450 行，`buildEQSQueries()` 约 140 行。建议按文件拆分 `EnemyQueries.cpp` / `EnemyBehavior.cpp`，`Enemy` 只保留状态与流水线。
5. **黑板性能契约**：键统一进 `Blackboard::Keys`（现在 `"world.threatSources"` 等魔法字符串硬编码在 5 处），并把键类型改成 `std::string_view` + 透明哈希，或落地已声明未用的 `BlackboardKey`；否则每步每敌人的字符串分配会成为规模化瓶颈。
6. **`main.cpp` 过长且职责过载**：命令行解析、截图、`SandboxLayer`、两阶段启动、手写主循环全在一个文件，且**手写主循环与 `GameLoop::run()` 逻辑重复**（快捷键若只改一边就会出现"只在这个入口才有的差异"）。建议拆 `CommandLine.{h,cpp}` / `Screenshot.{h,cpp}` / `SandboxLayer.{h,cpp}`，并给 `GameLoop` 加 `setLayer()` 以复用 `run()`。
7. **EQS API 防误用**：`distanceToTargetTest`（接近）与 `distanceFromTargetTest`（脱离）只差一个介词却语义相反，建议改名 `approachTargetTest`/`retreatFromTargetTest`；工厂函数加 `assert(rangeMax > rangeMin)`；空 `tests` 的查询静默返回空结果（`EQS.cpp:349-363`）建议打一次性告警，避免把配置错误当成正常结果。
8. **纪律建议**：A1 是"修复引入新 bug"的典型（注释描述的意图与代码不一致）。建议每处 `【修复】` 注释都配一条会失败的回归测试——这条在 `ROADMAP.md` 里已经总结过，但撤退分支没照做。
