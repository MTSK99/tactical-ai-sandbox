> 用途：面试 / 答辩 / 项目评审时照着讲。
> 结构：先给结论和数据 → 架构 → 一帧时序 → 五大系统（问题·决策·代价）→ 三个实测驱动

## 0. 30 秒电梯陈述

> 这是一个**战术 AI 沙盒**：C++17 + raylib，用行为树做决策、黑板传数据、EQS 选位置、
> A* 寻路、感知系统限制 AI 的信息来源。它不是游戏，是一个**可交互、可量化、可回归**
> 的 AI 实验场 —— 屏幕上能看到每个 AI 在想什么（视野锥 / 候选点评分 / 路径 / 行为树状态），
> 命令行能无头跑 60 秒并断言行为。

| 指标 | 数值 |
|---|---|
| 源码 | 40 个文件，约 **11,800 行**（引擎 2.1k / AI 3.0k / 游戏 4.0k / 调试 1.6k，其余为 `main.cpp` 与构建脚本） |
| 测试 | 15 个 `.cpp`，约 **4,800 行，281 个用例**，全绿 |

既有单元测试守着，也能在屏幕上用可视化当场看到。

## 1. 架构：四层，一条单向依赖

```
debug  ──▶  game  ──▶  ai  ──▶  engine
（可视化）  （世界）   （决策）   （时间/输入/渲染）
```

| 层 | 职责 | **刻意不做** | 主要文件 |
|---|---|---|---|
| `engine` | 窗口、渲染、输入、固定步长时间、中文字体图集 | 不知道"敌人""子弹"是什么 | `Time` `Input` `Renderer` `CjkFont` `GameLoop` |
| `ai` | 行为树、黑板、EQS、感知、A* 寻路 | 不依赖游戏层（地形以 **`LineOfSightQuery` / `NavGrid` 接口注入**） | `BehaviorTree` `Blackboard` `EQS` `Perception` `Pathfinding` |
| `game` | 实体、世界、伤害结算、子弹、玩家/敌人 | 不做渲染，不读输入 | `Entity` `World` `Player` `Enemy` `Projectile` |
| `debug` | 调试绘制与调参面板（读世界状态 + 改参数） | 不参与决策、不改实体状态 | `AIDebugDraw` `DebugUI` |

### 值得讲的两个设计点

**1）`ai` 层不认识 `World`。**
`Enemy` 需要"我能看到那儿吗""那儿能站吗"，但它拿到的不是 `World*`，而是两个注入的
函数对象 / 只读数据结构：

```cpp
enemy->setNavGrid(&navGrid_);                       // 只读地形
enemy->setLineOfSightQuery(makeLineOfSightQuery()); // 视线：两个点 → 通不通
```

好处：AI 模块可以脱离世界单独做单元测试（测试里构造一个手写地形即可），
依赖方向不会反向，改了游戏层不会波及 AI 层。

**2）`World` 用 `unique_ptr` 拥有全部实体，对外只给 id。**
外部拿到的指针都是**短期使用**的（当帧内）。这条规矩消灭了"遍历中删除实体导致悬垂"
这一整类崩溃 —— 也正因为踩过坑，后来专门加了回归测试（见 §4 的删除路径）。

## 2. 一帧是怎么跑的（时序是最容易被追问的地方）

### 2.1 时间：固定步长 + 累加器

- 逻辑固定 60Hz（`--fixed-delta` 可调），渲染帧率不限（现场实测 120FPS 渲染 / 60Hz 逻辑）。
- `Time` 负责：累加器、`kMaxStepsPerFrame`（防"死亡螺旋"：一帧最多补几步）、
  插值系数 `interpolationAlpha`、慢动作（`timeScale`）、暂停、暂停时单步。
- **为什么必须固定步长**：AI 的计时器（反应 0.25s、冷却 0.95s、搜索 8s）都按逻辑时间走，
  变步长会让"同样的操作在不同帧率下得到不同的战斗结果"。

### 2.2 `World::update` 的六个阶段（顺序本身就是正确性）

| # | 阶段 | 为什么在这个位置 |
|---|---|---|
| 1 | 收集 AI 输入（感知目标 / 威胁源 / 小队情报） | 必须早于所有 AI，否则这一步读到的是上一步的情报 |
| 2 | 驱动所有敌人 AI（计时统计） | AI 只产生**意图**，不直接改世界 |
| 3 | 开火（意图 → 真子弹） | 顺序反了就会出现"子弹比决策先出现" |
| 4 | 子弹逐段飞行与命中结算 | 伤害发生在**子弹到达**那一刻，不是扣扳机那一刻 |
| 5 | 回收终止的子弹 + 留弹着残影 | 先结算再回收，否则残影丢失 |
| 6 | 物理积分 + 边界约束 | 子弹的位移已在阶段 4 算过，不能再走通用积分 |

### 2.3 `Enemy::updateAI` 的五段流水线

```
感知 → EQS 位置查询 → 寻路 → 决策（行为树 tick） → 移动
```

**讲解点**：这个顺序不是为了好看，而是每段都在为下一段准备数据。
例如 EQS 需要"最后已知位置"（感知产出），行为树需要 EQS 的候选评分（选位产出），
移动又需要行为树写入的 `moveTarget_`。

**两条"顺序即正确性"的实例**（可以直接讲成踩坑故事）：

1. `firedThisStep_` 的唯一清零点在 `updateAI` 开头。当 F2 冻结 AI 时若跳过它，
   "冻结"就会变成**无限机枪**（每步都替它发射一颗，而且绕过冷却）。
   → 修复：冻结分支也必须 `clearStepIntent()`。
2. 玩家开火的请求（`firePending_`）由固定步消费。请求来自渲染帧的输入边沿，
   **两者不同频**时就会丢事件（§4 故事一）。

## 3. 五大系统：问题 · 决策 · 代价

### 3.1 行为树（`ai/BehaviorTree.*`）

**问题**：AI 行为要能组合、能调试、能实时看到"它现在卡在哪个节点"。

**决策**：
- 三类节点：组合（Selector / Sequence / Parallel）、装饰（Cooldown / Inverter / Repeat…）、叶子（Action / Condition）。
- 条件节点默认**不缓存**（每一 tick 重算）——因为本树的条件全都在描述**外部世界**，
  缓存会让"没看见玩家"永远冻结在第一次求值的结果上。
- 状态机：`Success / Failure / Running`；`abort()` 与 `reset()` 成对出现（跨帧行为被打断时必须清理）。
- 根节点用**反应式选择器**：每 tick 从最高优先级分支重新评估。
  否则"巡逻分支 Running"会把选择器粘住，交战分支永远轮不到。

**代价**：反应式选择器每帧重新评估整棵树（这里树很小，实测 AI 平均 0.003~0.004ms/enemy/step）。
更真实的代价是**语义陷阱**：见 §4 故事四（低优先级分支每帧被重启）。

### 3.2 黑板（`ai/Blackboard.*`）

**问题**：AI 各系统（感知 / EQS / 行为树 / 移动）之间要传数据，但不想让它们互相认识。

**决策**：`unordered_map<string, std::any>`，每条记录带**类型索引 / 版本号 / 写者 / 写时间**。
- 版本号：让"这条数据是不是我上次看的那条"可判断。
- 写者 + 写时间：调试面板上能直接看到"这条数据谁写的、什么时候写的"。
  → 这正是后来发现 `lastWriteTime` 恒为 0（`set()` 没有时间参数）的入口。

**代价（必须主动讲，这是这套方案的软肋）**：`std::any` 是**类型擦除**的，
写入 `std::vector<int>`、读取 `std::vector<EntityId>` 不会报错，只会**静默返回空**。
项目里为此写下一条硬规矩：

> 实体 ID 一律用 `EntityId`（`uint32_t` 别名）读写，绝不用裸 `int`。

（顺带：`get<T>()` 按值返回，读 `vector<vec2>` 会整份拷贝 → 后来补了零拷贝的 `getPtr<T>()`。）

### 3.3 感知（`ai/Perception.*`）——**这个项目最重要的系统**

**问题**：AI 如果直接读玩家坐标，玩家立刻会感觉"这敌人开挂"。
可信度来自**限制信息来源**，而不是提高计算量。

**决策**：四件套 + 一条不变量。

| 机制 | 默认值 | 作用 |
|---|---|---|
| 视野距离 | 480 | 太远看不见 |
| 视野半角 | 45°（共 90°） | 背后看不见（贴脸 60 单位例外） |
| 视线遮挡 | 开 | 墙后看不见 |
| 反应延迟 `reactionTime` | 0.25s | 持续可见 0.25s 才"确认"，避免瞬现瞬反应 |
| 记忆 `memoryDuration` | 6s | 丢失视线后仍"记得"，可以朝最后已知位置搜索 |

> **不变量：`confirmed ≠ visible`。**
> "确认目标"在记忆期内**一直为真**（那正是记忆的定义），它只回答
> "我还记不记得他"，不回答"我现在看不看得见他"。
>
> 这条不变量是项目里最多 bug 的发源地 —— §4 的故事二、故事三都是从它长出来的。

感知的输出全部写进黑板（`nearestEnemy` / `nearestEnemyDistance` / `lastKnownEnemyPosition` /
`threatLevel` / `timeSinceSeenEnemy` / `visibleEnemies`），行为树与 EQS 只读黑板。

**情报分层**（这是"像人"的关键，也是很好的讲解点）：

| 信息 | 谁能用 | 能不能开枪 |
|---|---|---|
| 自己看见的（confirmed + visible） | 交战分支 | **能** |
| 自己的记忆（最后已知位置） | 搜索分支 | 不能 |
| 队友广播的情报（`broadcastSquadIntel`） | 搜索分支 | 不能 |

也就是说：**队友告诉你"他在那边"，你可以过去搜，但不能隔墙开枪**。
情报由 `World` 每步汇总广播（取全队最新鲜的一次目击），有效期 24 秒；
报告者阵亡后他最后的目击仍然算数。

### 3.4 EQS（`ai/EQS.*`）——环境查询

**问题**：AI 要选"站哪儿"（掩护、射程、安全）。写成一串 `if-else` 会立刻变成没法调的
意大利面，而且**没法解释"它为什么站这儿"**。

**决策**：标准 EQS 三段式。

```
生成器（候选点） → 评估项（打分） → 排序取最优
       ↓                  ↓
  grid / ring / 点列表    measure + 曲线 + 区间 + 权重 + 过滤
```

- 评估项：`measure(候选点, 上下文) → 原始值`（距离、掩护度、威胁度…），
  再经 `curve(rangeMin, rangeMax)` 归一化到 `[0,1]`，乘权重求和。
- 曲线方向是**最容易搞反**的地方：`InverseLinear` 表示"原始值越小越满意"（如威胁度），
  `Linear` 表示"越大越满意"。项目里就修过一个反的：无目标时距离测试返回 0，
  归一化后是最低分，注释却写着"给满分"。
- `minAcceptableScore`：低于它就视为"没有可用位置"，上层必须能处理"空手而归"。
- NaN 防护：自定义 `measure` 很容易算出 NaN，而 `std::clamp` **对 NaN 原样返回**，
  于是 `score < 阈值` 恒为 false（NaN 比较永远 false）→ 候选不但不被淘汰，
  还会带着 NaN 进 `sort`，比较器失去严格弱序 = **UB**。
  → 统一在打分入口把非有限值压成 0（=最差）。

**代价**：候选数量与评估项数量相乘。所以有候选上限、有节流（`repositionInterval = 2.5s`），
以及"距离合适就原地打，别每帧换位置"的早退分支。

### 3.5 寻路（`ai/Pathfinding.*`）

**决策**：`NavGrid`（1600×1200，格 32 → 50×38）+ 加权 A*。

- 手写**二叉堆** + `heapPositions_` 反查表（否则"降低 g 值后上浮"找不到节点）；
- 8 邻域，对角代价 √2，启发权重 1.15（**加权 A\***：更快、允许非最优 —— 战术游戏常见取舍）；
- 贴角通行附加惩罚（让路径倾向走开阔处，看起来更自然）；
- **允许部分路径**：目标不可达时返回"能走到的最远处"，上层据此继续靠近；
- 平滑：用视线拉直折线，去掉网格锯齿；
- 健壮性三件套：起点/终点救援（起点被卡在墙里时用螺旋搜索找可站立点）、
  卡住超时（2.5s 没进展就换目标）、预算上限（`maxExpandedNodes`）。

**代价 / 教训（务必讲）**：**网格是"给移动用的膨胀表示"，不能拿它判视线和弹道。**

`NavGrid::fillRect` 用矩形角点 `floor` 填格：障碍**压住某格的一部分**，整格就被标成阻挡。
于是每个掩体的阻挡范围比它看起来的样子向外多出 **0~32 单位**。
拿这个格子判视线/子弹 → "贴墙就隐身、子弹离墙一格就消失"（§4 故事三）。
正确做法：**寻路/站立用膨胀格（实体需要身体间隙），视线/弹道用精确几何（线段×矩形）**。

## 4. 三个"实测驱动"的工程故事（最有讲解价值的部分）

> 这三个故事都是我在这份代码上真实做过的：**现象 → 假设 → 实测复现 → 根因 → 修复 →
> 对照实验证明测试有牙齿**。讲这种故事比讲架构更能体现工程能力。

### 故事一：玩家"点了没反应 / 有时候射不出来"

- **现象**：手按开火，有时出了一发，有时什么都没有；节奏时快时慢。
- **关键线索**：现场截图里 `frame 420 / 逻辑步 209` —— **120FPS 渲染 + 60Hz 逻辑，
  近一半的渲染帧根本没有逻辑步**。
- **根因**：输入"按下"事件只存活**一帧**（`state.pressed = nowDown && !state.down`），
  而消费发生在**固定逻辑步**里。落在"没有逻辑步"那一帧的点击**整帧蒸发**。
  帧率越高丢得越多（60FPS 下几乎看不出来，144/240Hz 上就是"手感莫名其妙"）。
- **修复**：按下事件**跨帧锁存到被消费为止**（上限 8 帧防"暂停很久之后补一枪"）；
  `isKeyPressed` 这类**非消费**读取仍然是严格帧内语义。
  同类问题一并修好：翻滚（空格）、重开（回车）、增兵（N）、imgui 面板点击。
- **附带收获**：排查中发现"无头宏只加在测试目标上，引擎库是正式配置编译的"，
  导致测试里每帧都被判为"失焦"而清空输入 → 输入层根本无法被测试。
  改成运行时判断 `IsWindowReady()`。
- **量化**：新增端到端测试（120FPS 渲染 + 60Hz 逻辑 + 每 0.117s 点击一次），
  回退修复后 **86 次点击只打出 43 发（正好一半）**。

### 故事二：敌人对着"空位置"开枪

- **现象**：敌人朝着没人的地方连开好几枪。
- **根因（两层）**：
  1. 开火用的目标位置来自 `kLastKnownPosition` —— 敌人**记忆**中的位置。玩家离开视野后
     这个点停在原地，而"确认目标"在 6 秒记忆期内**仍然为真** → 交战分支继续开枪。
     LoS 检查也救不了：那个空点自己有视线（它当初就是视线内才被记下的）。
  2. 更深的一层：`updatePerception` 用 `hasConfirmedTarget()` 判断"重新确认目标"，
     于是"搜索 → 到达 → 观察 → 放弃"的结果**下一步就被清掉**，搜索动作被无限重播 ——
     敌人被钉在最后已知位置上发呆（实测原地 3.5 秒以上）。
- **修复**：新增两个参数把"记得"和"看得见"分开 ——
  `fireTargetMaxAge = 0.15s`（距上次**真正看见**超过它就不开枪）、
  `engageLostGrace = 0.5s`（失联超过它就把战场交给搜索分支）；
  `updatePerception` 改用"距上次真正看见的时间"（`timeSinceLastSeen`）判断重新接触。
- **量化**：干净场景 **9 发里 7 发打空（连续 6 秒）→ 0 发打空**；
  真实关卡 60 秒 **31 发 / 2 发打空 → 0 发打空**。
- **顺便修好**：`lastSeenEnemyTime_`（小队情报的时间戳）在"只是还记得"期间被刷新，
  等于把情报一直标成"刚刚看到的"。

### 故事三：靠在墙边就"隐身"（顺带免疫子弹）

- **现象**：贴着墙站，敌人发现不到自己。
- **根因**：视线和弹道都用**被膨胀过的阻挡格**判定。测例：墙面在 `x=700`，
  而 700 落在格 21（`[672,704]`）里 → 整格变阻挡 → **阻挡范围比墙面胖了 28 单位**。
  贴墙站（距墙 12 单位）正好在这个"膨胀区"里。
- **量化（修复前 → 修复后）**：贴墙被看见 `否 → 是`；贴墙目标掉血 `0 → 18`；
  隔墙被看见 `否 → 否`（掩体仍有效）；隔墙目标掉血 `0 → 0`。
- **修复**：视线改为"线段是否穿过障碍矩形"（slab 法），弹道改为"点是否落在障碍矩形内"；
  **导航网格保持不变**（它仍是寻路/站立的权威）。
- **附带收获**：判定现在读**活着的实体**而不是派生网格数据 →
  "障碍被移除后留下看不见的墙"这一整类问题对视线/弹道免疫。

### 讲故事的方法论（这段本身就是加分项）

1. **不接受"应该是这样"**：三个故事都先用**可复现的测量**把现象钉成数字
   （丢帧率、打空比例、掉血值）。
2. **对照实验**：修完之后**回退修复**再跑测试，确认测试**变红**才留下它 ——
   否则就是"没有牙齿的测试"（项目里确实删掉过一条自己写的、回退后依然通过的测试）。
3. **把结论写成测试**：每个故事都留下 2~3 条回归测试，名字直接写清契约
   （`DoesNotFireAtRememberedPosition`、`HitsTargetHuggingWallButNotThroughIt`）。
4. **顺手记录"没做的事"**：无法证明有效的改动标成"防御性改动"而不是"修复了 bug"。

## 5. 测试策略

**为什么能无头测**：三点，按重要性排序 ——
1. **"要不要窗口"是运行期参数**（`Renderer` 构造函数的 `createWindow`，传 false 时
   不碰任何 GL/GLFW 调用），不是构建期宏。这样"无头"与构建配置无关，
   可以直接在单元测试里构造引擎对象并断言（`tests/test_renderer_headless.cpp`）。
2. 测试只链接逻辑层，不启动 `GameLoop`；
3. `TACTICALAI_HEADLESS_TEST` 宏只作为"我是测试构建"的标记保留 ——
   **不要**指望引擎里的 `#if !defined(...)` 守卫在测试构建里生效，
   它只作用于测试自己的翻译单元（这一点在 `tests/CMakeLists.txt` 里写明了）。

**281 个用例大致分三类**：

| 类型 | 例子 | 特点 |
|---|---|---|
| 纯逻辑/数据结构 | 行为树节点语义、黑板读写与类型、A* 结果几何、EQS 归一化与曲线 | 不依赖世界，快 |
| 行为契约 | 低血量必须远离威胁源、冷却期内不得超发、搜索会放弃、情报会过期、翻滚总位移恒为 150 | 驱动真实世界跑若干秒后断言 |
| 几何/物理 | 可站立判定、子弹不穿墙、贴墙可见、掩体挡子弹 | 位置刻意摆成能区分真假实现 |

**三条经验**（都是这项目里真实踩出来的）：

1. **恒真断言比没测试更糟**：`EXPECT_TRUE(x || !x)`、`EXPECT_TRUE(a || !a)` 这类
   重言式会让"有测试"变成假象。项目里清掉过几条。
2. **前置条件要断言**：测试里先 `ASSERT_TRUE(前提)` 并写明"若失败说明测试前提不成立"，
   否则失败信息会指向错误的方向。
3. **测试前提本身可能是 bug**：有一条冷却测试（"冷却更短就该打出更多子弹"）
   在修好 AI 之后失败了 —— 根因是**4 个敌人会在 25 秒内把玩家打死**，
   两组都被"打死玩家所需的枪数"截断。修法是把玩家血量设为 1e6，让指标真正反映射速。

**渲染无法单测**（这是很好的诚实点）：像素与手感没有断言。对策是
`--shot <file> --shot-frame N` 截图 + `--auto-roll`（连翻滚这种"只有视觉"的功能也能拍到）
+ `--dump`（无头打印世界快照）。

## 7. 预设问答

**Q：为什么用行为树，不用状态机 / GOAP / HTN？**
状态机在"多个条件同时影响行为"时会状态爆炸（本项目的敌人有 撤退/交战/搜索/巡逻 四条
并行关注点）。GOAP/HTN 更"聪明"，但**决策过程难以可视化、难以调参**，而这个项目的目标
恰恰是"让人看懂 AI 在想什么"。行为树是这三者里可解释性/表达力的最佳折中；
调试面板能直接显示"当前卡在哪个节点"。

**Q：AI 会不会开挂？**
不会，而且这是**设计约束**：AI 的输入只有感知系统写进黑板的那几个字段。
`resolveTargetPosition` 读的是 `kLastKnownPosition`（记忆），不是玩家实体坐标。
EQS 的上下文同样来自黑板。这条约束甚至制造过一个 bug（对着记忆位置开枪），
我们选择"修好它"而不是"让 AI 读实时坐标"。

**Q：子弹为什么是实体，不是瞬时射线？**
因为"能被躲开"是这个沙盒的核心玩法之一：翻滚有 0.25 秒无敌帧，
敌人的预判射击（`aimPrediction`，按自己观察到的目标速度差分出提前量）会打空。
HUD 上的"闪避"计数就是这套博弈的可观测证据。代价：要做子步进防穿透、要算提前量。

**Q：子弹怎么防穿透？**
每步位移切成 ≤6 单位的子步（60Hz 下子弹每步约 13.7 单位，而敌人半径只有 11，
一步跨过会"骑"在目标两侧），逐段检测地形与目标。

**Q：为什么固定步长？**
AI 的计时器（反应、冷却、搜索窗口）全部按逻辑时间；变步长会让同样的操作
在不同帧率下产生不同结果，AI 行为不可复现、测试也无从下手。
慢动作/暂停通过 `timeScale` 与"暂停时不产生逻辑步"实现，而不是改步长。

**Q：黑板用 `std::any` 的代价？**
类型错误是**静默失败**（返回空），所以项目里定了一条硬规矩：实体 ID 一律用 `EntityId`。
另外 `get<T>()` 按值返回，大对象（路径 `vector<vec2>`）每次读都会拷贝 → 补了 `getPtr<T>()`。
如果重做，会考虑"键=编译期句柄 + 类型安全容器"的方案。

**Q：AI 会卡死吗？**
设计上做了三层：巡逻点用了"多半径环 + 可站立判定"（贴边敌人不会选到地图外）、
寻路的起点/终点救援（螺旋搜索最近可站立点）、卡住超时（2.5 秒没进展就换目标）。
另外 `followPath` 有一个专门分支处理"部分路径走到头但人没到"的情况 ——
早期把它当成"到达"，结果敌人永久冻结在半路（实测 4 个敌人有 3 个卡住）。

**Q：性能怎么保证？**
- 每步每敌的 EQS 有节流（2.5 秒重评估）；感知每步一次；
- 消除每步的堆分配（黑板写入前先比对内容、`bindings()` 返回 const 引用、
  `getPtr` 零拷贝）；
- 寻路用预分配数组 + 手写二叉堆，A* 状态复用不重建；
- 实测：**每逻辑步、全部敌人（示例关卡 3 个）的 AI 总耗时 0.003~0.004ms**
  （沙盒 HUD 上直接显示 `AI x.xxx ms`，60Hz 下相当于每步预算的 0.02%）。

**Q：如果继续做，下一步做什么？**
按性价比排序：① 敌人之间互相感知（友军伤害/阵型保持）；
② 听觉/最后开火位置作为第二信息源；③ 巡逻环从"出生点"改为"当前位置"（跑远后不必回原位）；
④ 行为树可视化编辑器 / 决策回放录制（把"AI 为什么这么做"变成可回放的证据链）。

## 8. 诚实清单（主动讲限制，比被追问好）

| 限制 | 说明 |
|---|---|
| 只有视觉感知 | 没有听觉/声音/脚印；玩家蹲下也不会降低被发现概率 |
| 敌人之间不互相感知 | 无双友军伤害、无阵型；只有"小队情报"这一条共享通道 |
| 巡逻环以出生点为圆心 | 搜索跑远后放弃，会走回出生点附近巡逻（战术观感上不够自然） |
| EQS 候选上限与平滑是硬编码 | `smooth` 是 O(n²) 的视线拉直，路径很长时会变慢 |
| 生成文件写入源码树 | `GeneratedGlyphs.h` 由构建期脚本生成在 `src/` 下（多构建目录会互相覆盖） |
| ~~无头宏只作用于测试目标~~ | **已修**：改成运行期参数 `Renderer(..., createWindow)`，守卫不再依赖宏；并加了 `test_renderer_headless.cpp` 守着（对照实验：传 true 时确实会开窗+烘字体+建纹理，262ms） |
| 数值平衡是"能玩"级别 | 射程 400（玩家 520）、冷却 0.95s、反应 0.25s 等是手工调出来的，不是调优结果 |
